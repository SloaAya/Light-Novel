# Moon+ Reader（静读天下）云端缓存结构分析与 OPDS 集成评估

> 分析对象：`F:\Apps\Books\.Moon+`
> 数据来源：本机真实缓存（只读采样，未做任何写入）
> 复现工具：`python -m tools.moon_cache --join`（见文末附录）
> 日期：2026-09-15

---

## 0. 一句话结论

`.Moon+` 是 Moon+ 的**跨设备同步目录**，里面有三套互相独立、通过「**书名字符串**」串起来的数据：

| 数据 | 内容 | 覆盖度 | 对 OPDS 的价值 |
|---|---|---|---|
| `Cache/*.po` | 每本书的**阅读位置** | 128 本（已打开过的） | ⭐⭐⭐ 阅读进度 / 继续阅读 / 自动「已读完」 |
| `books.sync` | **书架全量元数据**（作者/简介/**系列+卷号**） | 1341 本（全库） | ⭐⭐⭐ 系列分组、卷号、简介补全 |
| `Cover/*.png` | 渲染好的封面 | 1315 本 | ⭐ 备用封面源 |

**推荐路径**：先做「只读消费」（方案 A，三步走），把 OPDS 从「静态书库」升级成「知道你读到哪的书库」；
把 OPDS 变成 Moon+ 的 WebDAV 服务端（方案 B）技术上可行、但需要你改手机端配置且有被 Cloudflare 拦的风险，建议二期再评估。

## 1. 目录结构与真实规模

```
F:\Apps\Books\                      ← 云盘「Books」根目录（Moon+ 的库本体）
├── <书名>.epub  ×1335               ← 实体书，扁平存放，共 6.8 GB
│   （.epub 1311 / .txt 20 / .pdf 2 / .docx 2）
└── .Moon+                          ← Moon+ 的同步数据根
    ├── Cache/                      ← 阅读位置：128 个 *.po（全部），共 3.2 KB
    ├── Cover/                      ← 封面：1315 个 *.png（中位 164 KB，最大 4.4 MB）
    ├── books.sync      177,181 B   ← zlib 压缩的 JSON，解压 835,057 B / 1341 条记录
    ├── books.sorts         161 B   ← ZIP，内含 shelf.options
    ├── books.id             13 B   ← 本设备同步 id
    └── covers.id            13 B   ← 封面索引版本号（与 books.id 同值）
```

**几个关键事实（实测）**

- `Cache/` 里**只有 `.po`，一个 `.an` 都没有** → 你目前没有同步任何划线/批注（`.an` 只在有高亮时才生成）。
- `Cache/` 是**扁平**的（无子目录），文件名 = **完整书名 + 原扩展名 + `.po`**，例如
  `GJ部 01.epub.po`、`DM杂志2017年11月附赠小册子 学生手册.pdf.po`。
- 128 ≪ 1341：**`.po` 只在「这本书被打开过」时才产生**，它天然是一份「读过的书」清单。
- `books.sync` 的 mtime（09-12 08:40）远旧于 `Cache/`（09-15 11:26）—— **位置是实时写的，书架元数据只在"同步书库"时批量写**。
- 1341 条记录 vs 1340 个唯一 `filename` → **存在同名重复条目**（`filename` 在本目录下不是唯一键）。

## 2. 文件格式与命名规则

### 2.1 `Cache/<书名>.<ext>.po` —— 阅读位置

纯 ASCII 单行文本，21–30 字节。实测样本：

```
1779019601627*0@0#0:0.0%        15卷MELON BOOKS特典 师傅不知弟子心.epub.po
1779019601627*3@0#10926:100%    26177868_第1章：…舔鸡巴.epub.po
1779019601627*34:100%           DM杂志2017年11月附赠小册子 学生手册.pdf.po
1753089022677*5@0#0:11.0%       GJ部 05.epub.po
```

文法：`dev * x @ y # z : p%`（PDF 无 `@y#z` 段）

| 字段 | 含义 | 本机实测证据 |
|---|---|---|
| `dev` | **Moon+ 设备 id**（13 位数字） | 128 个文件跨 11 个月只有 **2 个取值**；其一 = `books.id` = `books.sync[].deviceId`。**它不是时间戳**（社区早期猜测有误，但两者都是 13 位数，容易混淆） |
| `x` | PDF=逻辑页码；EPUB/MOBI=**零基 spine（章节）序号** | 分布 0–59，PDF 那条取 34 |
| `y` | 次级章节序号 | **本机 126 条全为 0**（说明这套书都是「一章一文件」的常规结构） |
| `z` | 该章节内的**零基字符偏移** | 0–12835；100% 那本取 10926，与 % 同向 |
| `p` | 进度百分比，**仅供显示** | 0% ×28 / 100% ×23 / 中间 ×77 |

> ⚠ 社区结论一致：**定位要同时用 `x/y/z`，不能只用 `p`**。`p` 是给人看的，用它跳转会跳偏。

### 2.2 `Cache/<书名>.<ext>.an` —— 批注/书签

- 本机**不存在**（没有划线）。
- 格式：**裸 zlib 流**，且前 2 字节被截断 —— 需要把 gzip 头 `1f 8b 08 00 00 00 00 00` 接回去再 gunzip。
- EPUB 会同时产生 `.po` + `.an`；**PDF 只有 `.po`**（PDF 支持批注但同步机制不同）。

### 2.3 `books.sync` —— 书架全量元数据（最有价值的一个文件）

- **zlib 压缩**（`78 9c`），解开是 UTF-8 的 **JSON 数组**，835 KB / 1341 条。
- 每条 12 个字段，实测填充率：

| 字段 | 非空 | 说明 |
|---|---|---|
| `filename` | 1341/1341 | **卷的实体文件名**（含扩展名）—— 与 `.po`、与实体书之间唯一的连接键 |
| `bookName` | 1341/1341 | 书名（去扩展名），12 条与 `filename` 不同 |
| `addTime` | 1341/1341 | 加入书架时间（ms 字符串），本机集中在 2026-09-10 ~ 09-12 |
| `deviceId` | 1341/1341 | 全部 = `1779019601627` |
| `category` | 1339/1341 | **系列 / 卷号 / 书架**三段式，见下 |
| `author` | 1319/1341 | 85 位作者；32 条是双作者用 `\n` 拼接（如 `葵せきな\n仙人掌`） |
| `description` | 755/1341 | 简介，平均 168 字，最长 407 字 |
| `downloadUrl` | 5/1341 | **仅云端、本地无实体**：`[WebDav]/Apps/Books/xxx.epub` |
| `favorite` / `rate` / `groupName` / `groupBooks` | 0 | 这四项功能你没用 |

**`category` 的三段式结构（1311/1341 条符合，覆盖 113 个系列）**：

```
<GAMERS电玩咖 番外>\n#5#\n轻小说\n
 ↑ 系列名              ↑ 卷号   ↑ 书架分类
```

- 卷号是**浮点字符串**（`1.0` / `10.5`），948 条带小数点 → Moon+ 原生支持小数卷号（和你库里 `第三之五卷` 的约定天然对齐）。
- 书架分类分布：轻小说 1197 / 武侠 70 / (TXT) 20 / 奇幻 7 / 后宫·人外·重小说·日本轻小说 各 1 / 空 42。

> 这个字段等于一份**已标注好的「系列 + 卷号」元数据**，而且是你自己维护的 —— 对 OPDS 来说是从天而降的好东西（见方案 A3）。

### 2.4 `books.sorts` / `books.id` / `covers.id`

- `books.sorts`：**ZIP 容器**（`PK\x03\x04`），只含一个 19 字节条目 `shelf.options` → `{"shelf_sort_by": 0}`。就是个排序偏好。
- `books.id` / `covers.id`：13 位数字纯文本，实测**两者同值**（`1779019601627`），等于 `books.sync[].deviceId`。
  语义 = **本设备的同步标识/接口版本号**，用来判断"云端数据是否来自同一台设备"。

### 2.5 `Cover/<书名>.<ext>_<n>.png`

- 命名 = 卷文件名 + `_<变体号>`，本机 1315 个**全部是 `_2`**（推测为"尺寸/质量档位"编号，未验证）。
- 这些是 Moon+ **渲染好后上传的封面图**，不是 epub 内嵌图 —— 质量不如直接从 epub 抽封面，但可作为兜底。

## 3. 缓存之间的关联：全靠「书名字符串」这一个外键

```
        Moon+ (Android)
              │  打开书 / 改标记
              ▼
   ┌──────────────────────┐
   │ Cache/<书名字符串>.po │  阅读位置（每本书一个）
   │ Cache/<书名字符串>.an │  批注（有高亮才有；本机无）
   └──────────┬───────────┘
              │  WebDAV / Dropbox / GDrive 同步
              ▼
   ┌──────────────────────────────────────────┐
   │ 云盘  Apps/Books/                        │
   │   ├─ <书名字符串>.epub   ← 实体书         │
   │   └─ .Moon+/                             │
   │        ├─ Cache/  ←───────┘  位置        │
   │        ├─ Cover/<书名字符串>.epub_2.png   │
   │        ├─ books.sync  ← 「书架同步」时批量写
   │        │    └─ [].filename ────┐ 连接键   │
   │        └─ books.id / covers.id │          │
   └─────────────────────────────────┼─────────┘
                                     │ CloudDrive2 挂载为 F:
                                     ▼
                          D:\Light-Novel 的 OPDS 书库
                          （同一批书，但文件名可能已被规整）
```

**三条必须记住的结论**：

1. **唯一的连接键是「卷的文件名字符串（去扩展名）」**。
   `Cache/GJ部 01.epub.po` ↔ `books.sync[].filename = "GJ部 01.epub"` ↔ `已完结/GJ部/GJ部 01.epub`。
2. **`books.sync` 是"全库视图"，`.po` 是"读过的那部分"**。
   1341 里有 1340 个唯一文件名，但有位置记录的只有 128 → 直接用 `.po` 存在性就能得到「读过的书」集合。
3. **`books.sync` 里有简介和系列卷号，`.po` 里有进度**，两者一 join 就是「按系列组织 + 带进度的书架」——OPDS 现在两样都没有。

### 3.1 与 D 盘 OPDS 书库的关联度（实测）

| 匹配策略 | 命中 | 比例 |
|---|---|---|
| 文件名严格相等 | 102 / 128 | 80% |
| ＋**卷号归一化**（`第X卷`↔`XX`、汉字↔阿拉伯、补零、去标点） | **114 / 128** | **89%** |
| 剩余 14 条 | 不在书库里（成人向网文分章、`（精修版）`/`（台）`等后缀变体、带作者后缀） | — |

「卷号归一化」这一步**不能省**，因为这是实测出来的真实差异：

```
书库（D:）                           Moon+（F:）
在地下城寻求邂逅是否搞错了什么 第一卷.epub   ←→   在地下城寻求邂逅是否搞错了什么 01.epub
玩乐关系 第一卷.epub                ←→   玩乐关系 1.epub
剑姬神圣谭 第一卷.epub               ←→   剑姬神圣谭 01.epub
```

同 12 条靠归一化救回来的还有 `GAMERS电玩咖01`（连空格都没有）、`谁杀了勇者 - 02`、`败北女角太多了！SSS` 等。

> 这正好和你的历史操作对上了：你在书库里做过「`第X卷` → `XX`」的批量规整，
> 而 Moon+ 扫描的是**没改过名的那一份**（`F:\Apps\Books`）。**两份库的命名已经分叉了。**

### 3.2 与现有「已读完」功能的交叉验证（这个很有说服力）

`finished.json` 里现在有 12 部。用 `.po` 反推（该作品所有卷 100%）：

| 作品 | `.po` 侧 | 在 `finished.json`？ |
|---|---|---|
| 放学后，到异世界咖啡厅喝杯咖啡 | 6/6 卷已读，5 卷 100% | ✅ |
| 我的妹妹是最棒的配菜 | 9/9 卷已读，3 卷 100% | ✅ |
| 我和女友的妹妹接吻了。 | 4/4 卷已读，3 卷 100% | ✅ |
| 在朋友背后与你悄悄牵手… | 3/3 卷已读，2 卷 100% | ✅ |
| 杖与剑的魔剑谭 | 2/2 卷已读，1 卷 100% | ✅ |
| 为美好的世界献上祝福 | 7/39 卷已读，3 卷 100% | ❌（只读了 7/39，合理） |
| 谁杀了勇者 | 3/4 卷已读，2 卷 100% | ❌（还差 1 卷） |

**你手动标的「已读完」和 Moon+ 里的阅读进度高度一致** —— 说明自动派生是可行的，而且能用进度差异发现"标了但其实没读完"或"读完了但忘了标"。

## 4. 集成方案

### 方案 A（推荐）：只读消费 —— OPDS 读缓存，分三步落地

**不改变你现在的任何使用习惯**：手机照样用 Moon+ 读，同步照样走原来的 WebDAV/网盘，OPDS 只是**多读一个目录**。

#### A1 · 阅读进度 → 「继续阅读」

- **做什么**：新增导航入口「继续阅读」，按 `books.sync[].addTime` 或位置文件 mtime 倒序，列出 `0 < p < 100` 的书；
  每本书卡上显示进度条 + `已读 3/9 卷`；点进去直接进该卷详情页。
- **怎么实现**：
  - `tools/moon_cache.py` 已经有 `load_positions()` / `join_with_library()`，直接复用。
  - 渲染层：`feeds.py` 加一个 `progress_html()`；`_html_page` 的顶栏 tab 与 `feed_root` 导航各加一项。
  - 与现有 `updates.py`（新增卷提示）共用一个「作品级」聚合结果，别写第二份。
- **量级**：约 150 行（含页面）+ 20 条测试。

#### A2 · 自动「已读完」

- **做什么**：管理员视图里把「已读完」拆成两栏：**手动标记** | **Moon+ 自动判定**（某作品全部卷 ≥ 99%）。
  自动判定项旁给一个「确认并转为手动」按钮，保留你现有的 `finished.json` 语义不变。
- **关键设计取舍**（别踩的坑）：
  - **自动判定不能直接写 `finished.json`**。理由：`updates.observe()` 里有「出现新卷 → 自动从已读完剔除」的联动，
    如果自动判定每轮都重新写入，会和删除联动打架（读一遍 → 自动加回 → 又删 → 死循环）。
    正确做法是**派生视图**：`finished.json` 只存人工结论，自动判定每次现算、只读不写。
  - 阈值用 `>= 99%` 而不是 `== 100%`：实测有 `99.4%`、`99.0%`、`97.9%` 这类"读到底但百分比没到 100"的情况（Moon+ 的百分比是估算值）。
- **量级**：约 80 行 + 15 条测试。

#### A3 · 系列 / 卷号元数据 → 系列视图 & 更准的新卷识别

- **做什么**：用 `books.sync[].category` 的 `<系列>\n#卷号#\n书架` 三段式：
  1. 在书详情页显示「`系列名` 第 `N` 卷」（现在只有目录名和文件名可用）；
  2. 给 `updates.py` 一个**权威卷号来源**：现在判断"新增卷"靠文件名快照 diff，
     有了卷号可以识别「卷号跳跃」（如已有 #1–#5，突然出现 #8）并提示"中间缺 2 卷"；
  3. 提供「按系列浏览」的 OPDS 导航（113 个系列已经标好了）。
- **障碍**：`books.sync` 的 `category` 用的系列名来自 Moon+ 侧的书名解析，**和你书库的目录名不一定一致**（实测 113 个系列里，`不正经的魔术讲师与禁忌教典 DM杂志与发售特典篇` 这类是自动切出来的）。
  → 必须**先做关联、再采信**，关联失败的作品退回现有目录名逻辑。
- **量级**：约 200 行（含关联表持久化）+ 30 条测试。

### 方案 B（二期）：把 OPDS 变成 Moon+ 的 WebDAV 端点

**做什么**：让 Moon+ 直接同步到 `https://ranqing.ccwu.cc/Books/.Moon+/Cache/`，OPDS 既读又写 `.po`。
社区有成熟先例（spacebee 用 FastAPI 伪装 WebDAV，把 `.po` 落到 ATProto 上）。

- **服务端要补的 HTTP 方法**：`OPTIONS` / `PROPFIND`（列目录、返回 XML）/ `GET` / `HEAD` / `PUT` / `MKCOL` / `DELETE`（可能还有 `MOVE`）。
  当前 `OPDSHandler` 只有 `do_GET` / `do_HEAD` / `do_POST`；`BaseHTTPRequestHandler` 会自动把未知方法分派到 `do_<METHOD>`，**加方法本身不难**（各 20–30 行）。
- **真正的风险（按严重度）**：
  1. **必须先抓真实请求序列再动手**。Moon+ 未必只发上面几个方法，也可能带 `Depth` / `If-None-Match` / `Expect: 100-continue` 等头。
     建议第一步是做一个**只记日志、全部返回 207/200 的探针端点**，把手机的完整请求序列录下来，再按真实序列实现。**别照着猜测直接写。**
  2. **Cloudflare 会干扰**：免费版请求体上限 100 MB（整本书 PUT 可能超）、可能对 WebDAV 的 `PROPFIND` 有奇怪行为、缓存规则可能吞掉请求。绕法是把 WebDAV 端点单独挂一个不走 Cloudflare 的域名/端口。
  3. **Basic 认证**：Moon+ 只支持 Basic（我们已有），但**口令错会降级成访客**（当前 `_role()` 的设计），WebDAV 写请求会静默变成 403 —— 要在 `PUT` 路径上单独做严格校验，别复用访客回落。
  4. **写冲突**：两台设备同时 PUT 同一个 `.po`，最后写的赢。要按 `dev` 字段 + 文件 mtime 做「谁更新」判断并保留冲突副本。
- **收益**：不再依赖 F 盘网盘的中转，实时性从"分钟级"变成"秒级"，并且你能在网页端**反向设置阅读位置**。
- **结论**：可行，但工作量约是方案 A 的 3–4 倍，且**有一步"先录请求"的不可跳过的前置调研**。

### 方案对比

| | 方案 A（只读消费） | 方案 B（WebDAV 接管） |
|---|---|---|
| 改动范围 | 新增 `moon_progress` 模块 + 3 个页面 | 新增 WebDAV 端点 + 认证/冲突处理 |
| 要动手机配置吗 | **不用** | 要改 Moon+ 的 WebDAV 地址 |
| 依赖 F 盘网盘 | 是（读） | 否 |
| 实时性 | 网盘同步周期（分钟级） | 秒级 |
| 破坏性风险 | 极低（纯读） | 中（写路径 + Cloudflare + 冲突） |
| 建议 | **先做** | 二期 |

## 5. 兼容性问题清单（按风险排序）

| # | 风险 | 实证 | 对策 |
|---|---|---|---|
| R1 | **改名即断链** | 严格匹配只有 102/128（80%）；书库用 `第一卷`、Moon+ 用 `01` | 三级关联阶梯：严格 → 卷号归一化 → 模糊；并把**未命中数**当健康指标暴露出来（>5% 报警） |
| R2 | **文件名不是唯一键** | `books.sync` 1341 条 → 1340 个唯一 `filename`；书库 1659 文件 → 1523 唯一卷标题 | join 结果按 `(分类, 作品, rel)` 一对多处理，别用 dict 覆盖 |
| R3 | **网络盘读取极慢** | 见第 6 节，单文件 ~55 ms | 必须本地缓存 + 目录级 generation 校验 |
| R4 | **`.po` 的 `p` 不能用来定位** | 社区逆向 + 本机 `x/y/z` 与 `p` 不一致的样本 | 目标是"显示进度"就只用 `p`；一旦要"跳到位置"，必须 `x/y/z` 三件套 |
| R5 | **`y`（次级章节号）当前全为 0，不代表永远为 0** | 本机 126 条全 0 | 解析器要保留 `y`，UI 不要假设它是 0 |
| R6 | **PDF / TXT / DOCX 的 `.po` 语义不同** | PDF 无 `@y#z`，`x` 是页码；TXT 20 本 | 进度显示要按扩展名分支；非 EPUB 的"章节"不要显示成"第 N 章" |
| R7 | **`.an` 解码需要接 gzip 头** | 本机无样本，未实测 | 实现前先造一个高亮样本验证，别直接上生产 |
| R8 | **`books.sync` 是批量写的，可能滞后** | mtime 09-12，而 `Cache/` 是 09-15 | 元数据与进度分开对待：进度实时读，元数据按天级读并接受滞后 |
| R9 | **云盘内容是明文** | `books.sync` 含全部简介 + 完整书架；`.po` 含设备 id | 仅提示：这是既有事实（本来就存在云盘），本功能不放大风险 |
| R10 | **编码** | 文件名含 `！？：`、`’`、`&`、`\n`（多作者） | 一切路径处理走 `os.path`，别手工拼字符串；JSON 落盘用 `ensure_ascii=False` |

## 6. 性能：实测数据与设计对策（这一节最关键）

### 6.1 实测

`F:` 是 **CloudDrive2 挂载的网盘**（卷标 `CloudDrive`；注意 `GetDriveTypeW` 会报 `FIXED`，
**不能用盘符类型判断是不是网盘**，要看卷标/延迟）。同规模读放在 D 盘对照：

| 操作 | F:（网盘） | D:（本地） | 放大 |
|---|---|---|---|
| 读 128 个 `.po`（共 3.2 KB） | **6,747 – 7,288 ms** | 53 ms | **≈137×** |
| 128 次 `os.stat` | 25.6 ms | 5.7 ms | 4.5× |
| `books.sync` 读取 + zlib 解压（177 KB → 835 KB） | 54.8 ms | — | 单文件，可接受 |

即：**每个小文件约 55 ms 的网络往返**。这条决定了整个设计。

### 6.2 对策

1. **绝对禁止在 HTTP 请求路径上读 `F:` 的 `.po`。**
   首页/列表页一次请求要拿 128 个位置 → 7 秒响应，完全不可接受。
2. **本地缓存 + 两段式校验**（`tools/moon_cache.py` 已实现第一版）：
   - 缓存落 `.autosync/moon_cache/positions.json`（本地盘、gitignored）；
   - 校验戳用 `{文件名: [mtime, size]}` → 命中即 0 ms 返回（实测：第二次运行秒回）。
3. **再优化一档（推荐在正式集成时做）**：把校验戳降级为**目录级 generation**
   —— `os.listdir(Cache)` + `Cache/` 目录自身 mtime + 文件数，只需 1–2 次往返（约 150 ms），
   不必做 128 次 `stat`。目录 mtime 在 `.po` 增删改时一定会变（实测 09-15 11:26 就是一次写入），足够当变更信号。
4. **TTL + stale-while-revalidate**：OPDS 侧不要现读，起一个后台刷新线程（TTL 建议 5 分钟，
   和 `INDEX_TTL=30s` 分开配置），请求永远只读内存。刷新失败就继续用旧数据（网盘偶尔掉线不能拖垮书库）。
5. **上限保护**：`Cache/` 现在是 128 个文件；如果哪天涨到几千个（换设备全量同步），
   6.7 s 会变成 2 分钟以上。要在刷新线程里加"单轮最多读 N 个 / 总超时 T 秒"的保护，超了就记日志保留旧缓存。
6. **不要读 `Cover/`**（1315 个 PNG，中位 164 KB）= 至少 200 MB 网络流量。
   要封面就用现有 `get_cover()` 从本地 epub 抽，快得多也清晰得多。
